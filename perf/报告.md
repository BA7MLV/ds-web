# 性能与 SEO/GEO 最终报告

本轮针对首页首屏关键路径、独立 iframe 演示启动时机、非关键后台工作和站点 SEO/GEO 一致性完成优化。
工作区已完成构建、自动化测试、静态审计和本地真实浏览器 A/B 测量；没有部署或推送。

## 配对测量结论

`perf/bench/benchmark-final.json` 使用同一时段的 A/B 交替、冷缓存、统一限速和第三方阻断策略。
桌面与移动各测基线/优化 10 次，40/40 次通过。首页可用要求真实标题、导航、两个 CTA 连续两帧稳定且通过不触发导航的命中检查；
演示可用要求真实 iframe 应用有实质文字、启用控件和已消失的加载遮罩。

| 操作 | 口径 | 优化前 p75 | 优化后 p75 | 降幅 |
| --- | --- | ---: | ---: | ---: |
| 首页可用 | 桌面 | 4,705.8 ms | 1,750.1 ms | 62.8% |
| 首页可用 | 移动 | 4,496.7 ms | 1,583.3 ms | **64.8%** |
| LCP | 桌面 | 3,437 ms | 1,820 ms | 47.0% |
| LCP | 移动 | 2,988 ms | 1,611 ms | 46.1% |
| 演示真实控件可用 | 桌面 | 21,699.3 ms | 17,813.7 ms | 17.9% |
| 演示真实控件可用 | 移动 | 35,278.3 ms | 32,091.4 ms | 9.0% |
| 主动体验后演示可用 | 桌面 | 16,420.4 ms | 15,499.6 ms | 5.6% |
| 主动体验后演示可用 | 移动 | 30,759.9 ms | 29,906.3 ms | 2.8% |

移动首页目标是 p75 至少降低 50%；10/10 有效样本下实测改善 64.8%，目标达到。演示单独计时后仍然较慢，
这说明延迟 iframe 主要改善首页关键路径，没有把完整演示成本消失在指标之外。

## 优化贡献与代理指标

本轮采用合并后的最终 A/B 作为时间结论，未把不同代码轮次的单次测量拼成因果贡献。能复核的代理变化如下：

- 首页 head 关键本地资源 31 → 6，JS 入口/预载 28 → 4，gzip 1,162,047 → 120,684 B。
- 移动端 p75 请求数 248 → 219，编码资源字节 4,992,500 → 3,938,906 B。
- 移动端首页可用前主线程阻塞长任务 903 → 470 ms。
- Mermaid 首页图表实现预载 24 → 0；Tailwind utilities 260,244 → 4,257 B。

这些计数与首页/LCP p75 同方向下降；演示资源仍属于独立应用，未声称其依赖体积已经减少。

`scripts/ratchet-input.mjs` 已把报告转换为 huashu-flash `ratchet.py` 可读取的四组版本结构，
`perf/bench/ceilings.json` 锁定当前优化版的首页、LCP、演示和移动端代理 p75。当前结果已用零容差逐项检查通过；后续只有更低的结果才能用 `--update` 下调上限。

## 风险与回滚

- 演示首次主动体验仍有较高等待；若产品更重视演示立即可见，需要单独优化 demo 应用，而不是恢复首屏阻塞加载。
- Mermaid 引擎仍有大于 500 KB 的懒加载 chunk；它只在图表页面使用时付出成本。
- 统计从同步改为延后异步，需关注极早离开页面的统计丢失和 SPA 导航口径。
- 回滚时按组件与辅助模块成组恢复：Mermaid 配置/fence/组件，iframe 调度/预览，字体/统计，星空/延迟任务，以及 SEO helper/机器导出；恢复后重跑全部护栏。

当前没有线上变更，因此不需要线上回滚操作。
