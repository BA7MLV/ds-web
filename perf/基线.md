# DeepStudent 官网性能基线

## 结论

首页慢的主要原因不是一张大图，而是三套工作在首屏同时发生：

1. VitePress 首页预加载整套 Mermaid 图表实现。
2. 页面水合后立即 `eager` 启动完整 DeepStudent 演示应用 iframe。
3. `<head>` 内的 Google Fonts 样式和 51.la 脚本会阻塞关键渲染路径。

## 瓶颈排序

### P0：Mermaid 被全站注入并在首页预载

站点只有 `timeline.md` 使用一个 Mermaid 代码块，但 `withMermaid()` 包裹了整个 VitePress 配置。构建后的首页因此生成 24 个图表相关 `modulepreload`；仅 ELK 流程图和思维导图两个块就有 612,377 B gzip。

这部分既占网络，也会增加浏览器解析/编译 JavaScript 的压力，而且对首页完全无用。

### P0：首屏立即启动完整演示应用

基线的 `AppShell.vue` 在 `onMounted` 时立刻显示 iframe，并明确使用 `loading="eager"`。仅演示入口直接声明的 JS / CSS 已有约 340 KB gzip，还会继续动态导入应用壳及功能模块。

因此首页外壳刚完成水合，就与 iframe 抢带宽、CPU 和内存。视觉上的加载遮罩只遮住结果，没有减少实际工作。

### P0（网络条件相关）：同步第三方资源阻塞首屏

全站 `<head>` 中加载 Google Fonts 外部样式表，并同步加载 51.la SDK；二者都没有延后到首屏可用之后。外部域名一旦慢、被代理或连接不稳定，会直接放大白屏和首屏延迟。

### P1：首屏持续运行 Canvas 动画

`HeroStarfield.vue` 挂载时创建像素缓冲、遮罩、密度场和星点，并以 30 FPS 运行。它不是主要下载瓶颈，但会与页面水合和 iframe 初始化争主线程，移动设备更明显。

### P2：挂载后继续制造非关键网络请求

首页挂载后立即请求 GitHub Star 数，并在 idle/1.5 秒后预热其余三张功能 SVG。这部分应延后调度，但三张 SVG 只有约 12 KB gzip，不应与 Mermaid 和完整演示的量级混为一谈。

## 建议验证顺序

1. 先让首页不再预载 Mermaid 图表块，比较首页头部 gzip 体积和「打开到能用」。
2. iframe 改为静态骨架/截图优先，在接近视口、用户点击或主页面空闲且关键资源完成后再启动。
3. Google 字体改为自托管或系统字体；51.la 改为 `defer`/延后初始化，确认统计不丢失。
4. 再测星空动画在低端移动设备上的长任务和帧率，必要时首帧静态、空闲后动画。
5. 每次只改一项，前后版本交替测试至少 10 次，记录 p50/p75/p95。
