# 性能与 SEO/GEO 验证指南

## 静态生产产物审计

先构建，再审计实际输出；脚本不访问远程网站、不安装依赖：

```sh
npm run build
node scripts/audit-site.mjs
```

报告默认写入 `perf/bench/audit.json`，不通过时退出码为 1。检查覆盖：

- 可索引 HTML 的唯一 clean URL canonical 与 sitemap 一致，404 声明 noindex。
- JSON-LD 可解析；中文和英文落地页互相声明正确的 hreflang，未翻译的文档不输出虚假的互译关系。
- 站内链接和锚点对应真实文件，页面链接不遗留 `.html` / `.md`。
- 首页不预载 Mermaid 引擎/图表实现；轻量异步 `MermaidDiagram` 组件本身可存在。
- 页面不通过同步样式表阻塞加载 Google Fonts，51.la 外部脚本不存在同步加载标签。
- 已发布的 Markdown / llms 文本不泄露 Vue 源组件或内部计划。
- `llms.txt` 和 `llms-full.txt` 存在；不要求只有 Vue 组件的落地页额外生成空白 Markdown。

报告将 icon 与关键入口资源分开，并提供首页 head 所声明本地资源的 raw、gzip、Brotli 大小和最大的资源。
它不宣称覆盖全部运行时动态加载，也不把压缩大小直接等同于用户感知时间。

可指定另一份生产目录：

```sh
node scripts/audit-site.mjs --dist /private/tmp/ds-web-perf.tgon5E/baseline --output perf/bench/baseline-audit.json
```

## 浏览器 A/B 测量

当前保留的未优化产物在 `/private/tmp/ds-web-perf.tgon5E/baseline`。完成新构建后运行：

```sh
node scripts/bench-site.mjs \
  --baseline /private/tmp/ds-web-perf.tgon5E/baseline \
  --optimized docs/.vitepress/dist \
  --runs 10 \
  --devices desktop,mobile \
  --third-party block \
  --output perf/bench/benchmark.json
```

脚本优先加载项目已有 Playwright，然后尝试本机预置运行时。可以通过 `--playwright` 或
`--executable-path` 指定已安装的包/浏览器；脚本不会下载浏览器或依赖。

每个设备、每个版本各 10 次，共 40 次；相邻轮次交替 A/B 与 B/A，减少顺序偏差。
参数明确固定为下行 1.6 Mbps、上行 750 Kbps、延迟 150 ms、CPU 4 倍降速，
不使用含义随浏览器版本变化的网络预设名称。桌面视口为 1440 × 900，移动视口为 390 × 844。
每次使用新浏览器 context、清空并禁用缓存、关闭 service worker；本地服务对文本类产物使用 gzip，
同时声明 `Cache-Control: no-store`。OS DNS 缓存及浏览器进程启动耗时不计入测量。

默认把两个版本的一切第三方 HTTP 请求均明确阻断，逐条记录 URL 和策略；因此它隔离的是第一方成本，
不能用来估算 Google Fonts、统计服务或 GitHub API 在真实网络中的时间收益。需要另测真实外部服务时，
可使用 `--third-party live`，但必须另存报告并说明外网时延与失败不可控；不能混合两种策略的样本。

报告保留每次采样、成功/失败状态、有效样本数量与 p50 / p75 / p95，并分别观察：

- 首页真实标题可见时间；下载和快速上手 CTA 的可操作时间；导航和 CTA 稳定可用时间。
- 顶层文档 LCP、CLS、主线程长任务以及 iframe 长任务；请求数、脚本/样式数和传输字节。
- 演示收到 ready 消息的时间，以及真实应用内容与控件可以操作的时间。
- 首页可用后滚动到演示并触发开始按钮，记录「用户产生体验意图 → 演示能用」时间。

演示计时必须同时满足：iframe 中的应用已挂载、有实质文字、有启用且能命中的实际控件、外部加载遮罩消失，
且控件通过不触发副作用的可见性、启用状态和 DOM 命中检查。SSR 预览、骨架、单独的 ready 消息都不算演示完成。
首页 CTA 同样使用不触发导航的真实链接可见性、启用状态和 DOM 命中检查。

只有移动端两个版本都得到至少 10 个成功样本，才比较「首页能用 p75 降低 50%」目标。
仍需并列检查演示完成时间，避免把延后完整应用的成本遗漏。缺失或超时样本不会被写成 0。

## 当前环境限制

早期安全试运行在本地 HTTP 服务监听阶段曾返回 `listen EPERM: operation not permitted 127.0.0.1`，
失败记录保留在 `benchmark-launch-check.json`、`benchmark-recheck.json` 和 `benchmark-final-launch.json`，不作为成功数据。
随后在可启动本地服务和浏览器的环境中完成 `perf/bench/benchmark-final.json`：桌面/移动各 10 次，基线/优化共 40/40 次通过。
移动端首页可用 p75 从 4,496.7 ms 降至 1,583.3 ms，改善 64.8%；LCP 从 2,988 ms 降至 1,611 ms；演示真实控件 p75 从 35,278.3 ms 降至 32,091.4 ms。
因此 50% 的移动首页目标已由统一口径的浏览器样本验证，但这仍是本地实验室结果，不代表线上 CDN、第三方服务或 CrUX。
浏览器样本采用第三方统一阻断策略，不能据此估算 Google Fonts、51.la 或 GitHub API 的真实网络收益。
静态审计、生产构建与逻辑测试仍需在后续代码修改后重跑；它们也不能替代真实设备的视觉/交互冒烟。
`benchmark-final.json` 的每次采样、成功状态、p50/p75/p95、请求与字节明细均保留，最终汇总可直接复核。

## 棘轮上限

将最终浏览器结果转换为 `ratchet.py` 所需的版本结构，并检查当前上限：

```sh
node scripts/ratchet-input.mjs perf/bench/benchmark-final.json perf/bench/ratchet-result.json
python3 .agents/skills/huashu-flash/scripts/ratchet.py check \
  --result perf/bench/ratchet-result.json \
  --ceilings perf/bench/ceilings.json \
  --version mobile-optimized --metric ready --label homepage-mobile --tolerance 0
```

`perf/bench/ceilings.json` 锁定首页、LCP、演示和移动端请求/字节/阻塞长任务 p75；后续测量必须先通过检查，
确认更低后再用 `--update` 更新相应上限。规范化结果保留桌面/移动和基线/优化四组，便于逐项复核。

每项需求对应的代码、测试、产物证据与剩余浏览器门槛见 [验收清单](./验收清单.md)。
